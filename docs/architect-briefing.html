What we have built on this laptop

A full-stack learning-management application with a shared frontend, a Django API and persistent domain records. The recent work connects nine role-based module workflows. The repository also contains other LMS modules; this briefing does not claim that every module has received the same recent workflow validation.

Architecture description: a modular monolith with a separate frontend application. Domain modules share one Django application and database. They are not separate microservices.

Browser API calls go through the frontend proxy to Django. Django checks the signed-in account, action permission and record scope, saves validated changes, then returns authoritative data. The frontend refreshes affected views.

3. Data and synchronization

Core records include courses, cohorts, enrolments, lessons, completions, lectures, library loans, path steps/progress, preferences, tutor policies/flags and translations. Dashboards and reports calculate results from records instead of fixed frontend numbers.

Example: a learner completes a lesson; Django persists LessonCompletion. On the next fetch, the course reader, course progress, path progress and recommendation feed use that saved evidence. Updates occur after mutations, navigation, refresh or window focus where implemented. There is no universal real-time push.

Business records are database-driven. Page order, labels, capability mappings, validation constraints and some defaults remain defined in code. This is not yet a fully administrator-configurable workflow platform.

4. Security model

Local sign-in uses Django sessions, same-origin cookies and CSRF protection. Role permissions determine which action an account can perform. Tenant/campus, course assignment and learner enrolment determine which records it can access. Both checks belong to the backend; hidden buttons are not security enforcement.

Separate capabilities permit Coordinator tutor/path/translation work without granting assessment authorship. Learner records, flagged tutor excerpts and scoped reports have backend access checks. Provider keys stay on the server.

5. AI and background work

The tutor uses a direct Google Gemini adapter. It supplies published course text and applies course topic rules. This is an AI assistant integration, not an autonomous agent framework. It does not independently plan work or execute external tools.

Personalisation uses goal-term matching, pace limits and actual lesson/assessment/discussion records. Translation is human-entered and approved. Neither should be presented as an AI agent.

A separate quiz-expiry management command can finalize expired attempts while a browser is closed. It is a background worker, not an AI agent.

6. Evidence and production boundary

Latest recorded checks: 135 backend tests, 21 frontend tests and a successful production build. These verify defined behaviour; they do not establish production readiness. AI workflow tests use mocked responses. Native browser interaction and real-provider generation were not verified in the latest pass.

The repository includes production configuration and handoff material for Entra identity, PostgreSQL, Redis, private Azure storage, malware scanning, isolated code execution and institutional Jitsi. These require institution-owned services, secrets and staging acceptance. They are not evidence that those services are live on this laptop. No live production deployment has been performed, and recent changes have not rebuilt deployment archives.

Architect decisions: confirm the production tenancy model, review code-defined versus administrator-managed policy, validate PostgreSQL concurrency, define media/AI retention, test institutional integrations, and complete browser/accessibility/security acceptance before go-live.

7. Suggested laptop demonstration

  1. Open the local application and use issued development accounts. Do not show secrets or API keys.
  2. Show a course and its cohort/enrolment, then switch to the learner journey.
  3. Complete a lesson and refresh the related progress/path views.
  4. Show the tutor policy, learner flag and staff review workflow; clearly distinguish mocked test evidence from a live provider demonstration.
  5. Submit a translation, show learner original fallback, approve it and revisit the learner view.
  6. Use the module guides and verification record to explain scope and remaining acceptance work.
